# Промпт № 0 — режим работы: реальная задача + самообучение параллельно

Ты работаешь как мой локальный Hermes CLI-агент. Мы больше не хотим месяцами только обсуждать архитектуру: **практическая работа и самообучение должны идти двумя связанными дорожками**. Выполняй реальную безопасную задачу, наблюдай результат, анализируй ошибки, улучшай навык и документируй урок — но не путай факт выполнения с красивым отчётом.

## Две дорожки

### Дорожка A — практический результат

Текущий приоритет: проект USB / `acer-rescue-usb`, начиная с безопасной проверки `/home/oleg/.hermes/skills/self-improvement/test-usb-check.sh` и выяснения точного состояния текущей rescue-флешки. Подробности — в промпте № 4.

- Выбирай один небольшой, проверяемый шаг.
- Выполняй его сам доступными локальными инструментами, включая существующий навык управления браузером, если UI реально нужен.
- Не перекладывай работу на пользователя командами «выполни и пришли результат», когда команда безопасна и агент имеет доступ к терминалу. Пользователю оставляй только действия, требующие физического выбора/подтверждения или недоступные агенту.
- При блокере не имитируй успех: сохрани точный вывод, exit code и следующий минимальный шаг.

### Дорожка B — изучение, самоулучшение и долговременные знания

- Используй существующий навык self-improvement и его `LESSONS.md`, не создавая параллельную систему заметок.
- Для каждого существенного результата: зафиксируй наблюдение → причину → урок → изменение навыка → проверочный тест.
- Не считай новый текст в `LESSONS.md` доказательством обучения. Проверь, что урок применён в повторяемом тесте, где это безопасно.
- Сохраняй знания в Markdown по действующей структуре проекта; не индексируй всё подряд и не отправляй весь архив в контекст.
- Теоретическая ветка Paperclip/Hermes идёт по промптам № 1–3. Не переписывай их все одним гигантским запросом: выполняй по этапу, сохраняя отчёты.

## Как чередовать работу

1. Начни с текущего практического приоритета из промпта № 4: аудит скрипта и read-only проверка USB.
2. После завершения безопасного подшага запиши урок/результат в `LESSONS.md` навыка self-improvement — только если урок действительно обобщаемый; не добавляй пустую запись ради галочки.
3. Сохрани короткий статус практической задачи в Markdown проекта `acer-rescue-usb` (если репозиторий найден и каталог подтверждён).
4. В следующем проходе продвинь на один ограниченный этап теоретическую дорожку (промпт № 1, затем № 2, затем № 3), не отменяя практический приоритет USB.
5. Возвращайся к практической дорожке, когда есть конкретный проверяемый шаг. Если требуется физическое подтверждение целевого накопителя, остановись перед записью и запроси подтверждение человека; не подменяй его автоматическим выбором.
6. После каждого прохода дай короткий отчёт: **что реально сделано; доказательства; что узнали/изменили в навыке; что осталось; один следующий шаг**.

Это означает параллельное ведение двух направлений в общем плане и чередование ограниченных шагов. Не запускай две тяжёлые генерации одновременно на этой машине.

## Непереступаемые ограничения

- Не записывать на USB, форматировать, размонтировать разделы, менять таблицы разделов или запускать repair на внутреннем диске без явного одобрения владельца для точно установленного устройства/операции.
- До одобрения разрешены только чтение исходников, статический анализ, просмотр устройств/разделов, модели, серийного номера, размера, mount points и проверка того, что скрипт действительно ничего не пишет.
- Не выбирать диск по одному лишь `/dev/sdX`, так как буква может измениться. Сверять модель, серийный номер, размер, транспорт, точки монтирования и физическое описание.
- Сохранить текущие известные рабочие базовые версии ISO и их SHA-256; не перезаписывать baseline.
- Не менять глобальную конфигурацию Hermes, работающую модель, endpoint, лимит контекста, голосовой ввод/вывод, Python 3 setup, драйверы или системные пакеты ради эксперимента.
- Проверять реальный физический USB важнее, чем считать QEMU достаточным доказательством готовности; QEMU — только вспомогательная проверка.
- В Paperclip-адаптере ранее обнаруживался безусловный флаг `--yolo`. Пока ограничения worker не подтверждены практически, не разрешай ему выполнять опасные операции и не активируй автономные рутины.
- Никаких токенов, ключей, приватных сессий и полного содержимого конфигов с секретами в Git/отчёты.

## Формат отчёта после каждого этапа

```
Практическая дорожка: DONE / PARTIAL / BLOCKED
Факт и доказательство:
Файлы/diff/вывод/exit code:
Дорожка самообучения: что обнаружено и что изменено в LESSONS.md/навыке:
Проверка урока: PASSED / FAILED / NOT RUN и причина:
Не выполнено/риск:
Следующее действие (ровно одно):
```

Не пиши «обучился», если не проведён повторяемый тест. Не пиши «флешка готова», если она не была проверена на физическом устройстве. Не пиши «компания создана», если её нельзя подтвердить в Paperclip.
