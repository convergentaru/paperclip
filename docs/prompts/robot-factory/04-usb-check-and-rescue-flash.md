## Этап 1 — аудит скрипта, ничего не записывать

1. Проверь, существует ли указанный файл и покажи его размер, дату изменения и контрольную сумму.
2. Прочитай скрипт целиком. Проверь, есть ли `sudo`, `dd`, `wipefs`, `mkfs`, `parted`, `sgdisk`, `fdisk`, `blkdiscard`, `mount`, `umount`, `partprobe`, redirection в `/dev/*`, изменения разделов/файловой системы и прочие команды записи. Проследи все вызовы и функции, а не только поиск по ключевым словам.
3. Выполни только статическую проверку синтаксиса, например `bash -n`; `shellcheck` использовать только если уже установлен. Не устанавливай пакет ради этого.
4. Раздели функции на read-only и destructive/write-capable. Если функция записи вызывается автоматически, исправь скрипт обратимым минимальным diff или создай безопасный read-only режим по умолчанию. Без явного opt-in скрипт не должен ничего писать.
5. Создай копию исходного скрипта до редактирования. Не используй `chmod` как доказательство корректности скрипта; файл можно вызвать через `bash script.sh`, если это достаточно.
6. Если исходный код уже безопасен, не редактируй его без причины. Диагностируй, почему исходный запуск завершился `exit 1`, на основании реально полученного stderr/stdout и exit code. Не выдумывай прошлый вывод, если он не сохранился.

## Этап 2 — read-only инвентаризация USB

Выполни самостоятельно в доступном терминале только команды чтения. Например, если утилита поддерживается:
- `lsblk -J -o NAME,PATH,TYPE,TRAN,RM,SIZE,MODEL,SERIAL,FSTYPE,LABEL,MOUNTPOINTS`
- `findmnt`
- `udevadm info` для конкретного обнаруженного блочного устройства, если это нужно.

Покажи устройства с моделью, серийным номером, размером, транспортом, съёмным признаком, разделами и точками монтирования. Секреты не нужны; серийные номера можно оставить в локальном отчёте, но не публиковать их в GitHub.

Не угадывай устройство по `/dev/sdX`. Устройство может менять имя после переподключения. Не выбирай системный диск, диск с корнем `/`, swap или любое устройство с неясным назначением. Не размонтируй разделы, не запускай repair и не вызывай сценарий записи.

Запусти скрипт только в документированном read-only режиме, если по коду доказано, что этот режим не может ничего изменить. Если такой режим не существует или нельзя гарантировать отсутствие записи, не запускай скрипт на физическом устройстве — сначала исправь/раздели безопасный режим.

## Этап 3 — что считать тестом

Безопасный первый тест должен подтвердить только:
- скрипт корректно сообщает об отсутствующем/несуществующем устройстве;
- корректно обнаруживает и отображает реальное блочное устройство в read-only режиме;
- правильно показывает тип, размер и модель, если эти поля доступны;
- обнаруживает неоднозначный путь/системный диск и останавливается;
- не вызывает никаких write/destructive команд в этом режиме;
- выдаёт понятную ошибку и ненулевой exit code при некорректном аргументе.

Не эмулируй успешную запись и не считай запрос подтверждения достаточной защитой. На этом этапе не запускать даже тестовую запись.

## Этап 4 — физическая rescue-флешка

Проверь состояние проекта `~/projects/acer-rescue-usb`, не затирая изменения пользователя. Найди список образов, известные рабочие baseline ISO и зафиксированные SHA-256, а также отчёты предыдущих физических тестов. Не переименовывай, не редактируй и не перезаписывай known-good ISO. QEMU — вспомогательная проверка; реальный тест на записанном USB и физическом компьютере остаётся отдельным критерием.

Если найдена незавершённая работа по сборке rescue-флешки, выбери следующий **read-only или полностью обратимый** шаг и выполни его сейчас. Сначала не записывай ISO на носитель. Для реальной записи остановись и предоставь владельцу короткую карточку подтверждения: точные модель, серийный номер, размер, текущие разделы/данные, целевая операция и файл ISO с SHA-256. Продолжать запись можно только после явного одобрения владельца этой конкретной операции.

- Не проси пользователя выполнять команды, которые агент может безопасно выполнить сам.
- Не запускай весь проект сборки ISO заново без установления текущего состояния.
- Не меняй рабочий Hermes/голос/model endpoint/Python 3 и не запускай новую большую модель.
