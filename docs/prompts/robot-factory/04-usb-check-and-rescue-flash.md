# Промпт № 4 — загрузиться с уже записанной rescue-флешки и подключиться по Tailscale + SSH

**Текущая стадия — НЕ запись ISO.** По состоянию, сообщённому владельцем, rescue ISO уже записан на USB. Теперь нужно использовать этот носитель у удалённого Acer, загрузить rescue-среду и войти в неё с домашнего компьютера через Tailscale и SSH, чтобы выполнить первичную read-only диагностику внутреннего диска.

Не проси владельца подключать USB к домашнему компьютеру, чтобы повторно выбрать диск для записи. Фраза «в текущей системе нет USB» не является блокером для проверки уже записанного носителя. Не пересобирай образ и не повторяй процедуру записи, пока не будет найден конкретный дефект существующего ISO или физической флешки.

## Цель на этот запуск

Пройти максимально возможный путь:

1. На домашнем Ubuntu проверить готовность локального Tailscale, проекта и имеющегося ISO.
2. По коду проекта установить, действительно ли rescue ISO запускает сеть, Tailscale и SSH автоматически; определить ожидаемое имя/идентификатор узла и проверить, нет ли уже появившегося rescue-узла в tailnet.
3. Если удалённый компьютер уже загружен с USB и находится в tailnet — подключиться к нему через SSH и выполнить базовую read-only диагностику.
4. Если удалённый компьютер ещё не загружен, подготовить короткую инструкцию только для человека на месте: вставить уже записанную USB-флешку в Acer, выбрать загрузку с USB через boot menu/BIOS, дождаться запуска rescue-среды и сообщить экранные признаки/статус. Не просить его подключать флешку к домашнему компьютеру и не заставлять выполнять команды, которые можно выполнить удалённо.
5. Если Tailscale или SSH не заработает, установить конкретный слой отказа (не загрузилась ОС / нет сети / узел не зарегистрирован в tailnet / не работает SSH) и дать один следующий практический шаг. Не возвращаться к теории и не считать задачу завершённой простым перечислением возможных причин.

## Этап 1 — локальная проверка с домашнего Ubuntu

Работай через локальный терминал. Выполни и сохрани фактические результаты:

- `tailscale status`
- `tailscale ip -4`
- `tailscale netcheck`
- `getent ahostsv4 controlplane.tailscale.com`
- проверь доступность control plane тем безопасным способом, который уже использовался в проекте;
- `git -C ~/projects/acer-rescue-usb status --short`, текущий commit/branch, список файлов ISO с размером/датой и соответствующие манифесты;
- вычисли SHA-256 существующего `/home/oleg/projects/acer-rescue-usb/build/acer-rescue-v6-final.iso`, **только если файл существует**. Если его нет, найди существующие ISO в проекте и выбери кандидат на основе отчётов, не пересобирай образ по умолчанию.

Не меняй Tailscale, SSH, системные службы или firewall на домашнем компьютере, если не найден конкретный сбой. Не публикуй ключи, auth tokens, private keys, пароли или auth URLs. Не меняй рабочую модель, endpoint, голосовые настройки и конфигурацию Hermes.

## Этап 2 — проверить, что реально заложено в уже собранном ISO

Прочитай действующие исходники, скрипты сборки, конфигурацию автозапуска и тестовые логи в `~/projects/acer-rescue-usb`. Не делай выводы только по README или названию файла.

Установи:
- какой SSH-сервер/режим используется (OpenSSH, Tailscale SSH или иной — только по фактической конфигурации);
- как запускаются сеть и Tailscale;
- как rescue-образ получает доступ к tailnet: уже зарегистрированный узел, безопасно сохранённая конфигурация, auth key или ручная процедура;
- какое имя/hostname/идентификатор ожидается в tailnet;
- где лежат логи запуска Tailscale/SSH и как локально получить их на rescue-среде;
- есть ли автоматические повторы и как избежать публикации credentials.

Если нужные службы уже настроены и нет подтверждённого дефекта, не пересобирай и не переписывай ISO. Если обнаружен конкретный дефект, сначала подготовь исправление и новый кандидат отдельно, сохрани baseline и покажи точный diff; не выполняй повторную запись без отдельного подтверждения конкретной операции.

## Этап 3 — обнаружить удалённый rescue-узел и подключиться

1. Используй текущий `tailscale status` и подтверждённые имена/адреса, чтобы выяснить, появился ли rescue-узел. Не выдумывай hostname и не пробуй подключаться к случайным tailnet-узлам.
2. Если узел есть, проверь достижимость штатным Tailscale CLI (например, `tailscale ping <подтверждённое-имя-или-IP>`, если эта команда доступна в установленной версии).
3. Пробуй SSH к подтверждённому адресу/имени с использованием существующего, разрешённого способа аутентификации. Не отключай проверку host key глобально и не включай парольную авторизацию для всех интерфейсов ради быстрого обхода проблемы.
4. После входа выполни только диагностические read-only команды, соответствующие rescue-среде: hostname/uptime, kernel, сетевые интерфейсы и адреса, Tailscale status/IP, состояние SSH-службы, `lsblk`, `findmnt`, `swapon --show`, наличие Windows-разделов и логи загрузки/служб. Проверяй внутренний диск Acer в режиме чтения.
5. Сохрани точную команду подключения, время, результат и exit code. В отчёте можно показать hostname и Tailscale IP, но не секреты и приватные ключи.

## Этап 4 — если SSH не сработал, не начинай заново

Локально установи, на каком шаге произошёл отказ:
- **узел отсутствует в tailnet:** скорее всего rescue-среда не загрузилась, не получила сеть или не прошла регистрацию; не заявляй, какой именно вариант, пока это не подтверждено;
- **узел виден, но Tailscale ping не проходит:** проверь сетевой статус/логи и доступность узла;
- **Tailscale ping проходит, SSH не проходит:** проверь конфигурацию SSH, порт, службу, host key и метод авторизации по фактическим логам;
- **нет способа увидеть состояние удалённой системы:** запроси у человека на месте только конкретное фото экрана/сообщение или одно физическое действие, которое нужно для следующего решения.

Если в готовом ISO уже есть альтернативный поддерживаемый удалённый канал, оцени его по фактическим исходникам и наличию службы. Не устанавливай наугад VNC/AnyDesk/другие агенты и не пытайся заменить Tailscale неизвестным облачным сервисом. Если в образе нет ни одного рабочего канала, укажи конкретный выявленный дефект и подготовь минимальное исправление/новый кандидат, сохранив предыдущий ISO неизменным.

## Этап 5 — первая удалённая диагностика Acer

После реального SSH-входа:
- выясни, доступен ли внутренний диск и какие разделы/файловые системы видны;
- проверь наличие данных и состояние загрузочных разделов Windows только средствами чтения;
- установи, действительно ли проблема в загрузочных файлах/EFI, а не просто в порядке загрузки;
- не выполняй `fsck -y`, `chkdsk /f`, восстановление загрузчика, запись в EFI, изменение таблицы разделов, монтирование read-write или иные ремонтные операции без отдельного плана и подтверждения владельца;
- составь краткий диагноз на основе фактического вывода и предложи один следующий шаг восстановления после проверки данных.

## Этап 6 — самообучение только после фактической работы

Навык `/home/oleg/.hermes/skills/self-improvement/` и `LESSONS.md` — вспомогательные средства, не цель задачи. Исправляй только конкретную ошибку, увиденную в работе. Сохрани резервную копию и diff; добавь урок, если он полезен для других задач, и проверь его повторяемым тестом. Не трать текущий запуск на очередное переписывание уроков вместо установления SSH-соединения.

## Запрещено

- Не просить подключать уже записанную флешку к домашнему компьютеру только потому, что `lsblk` не видит USB там.
- Не записывать повторно и не пересобирать образ без доказанного дефекта.
- Не выполнять команды записи на внутренний диск Acer; не менять Windows и EFI.
- Не публиковать секреты Tailscale/SSH в GitHub/логах.
- Не менять глобальную конфигурацию Hermes, рабочую модель 8B, endpoint или голосовые функции.
- Не утверждать «SSH работает», пока успешный вход не подтверждён реальной командой и exit code.

Подготовь инструкцию для человека у удалённого Acer: загрузить уже записанную флешку; затем продолжи проверку как только rescue-узел появится в tailnet.
